# Repository Guidelines

An MVP baseline web app: Astro 7 server-rendered pages with React 19 islands, TypeScript, Tailwind 4, Supabase auth, deployed to Cloudflare Workers. Product scope: @context/foundation/prd.md. Stack decision: @context/foundation/tech-stack.md. Starter rules in full: @CLAUDE.md.scaffold.

## Hard rules

- Never commit secrets. `SUPABASE_URL` and `SUPABASE_KEY` go in `.env` and `.dev.vars`, both gitignored, copied from @.env.example.
- Do not edit the block between the `BEGIN` and `END` markers in @CLAUDE.md. The toolkit CLI rewrites it. Do not write under `context/archive/`.
- Every new Supabase table gets RLS with one policy per operation and role. Per-user data isolation is a PRD guardrail.
- Business logic must not change auth, deploy, or pipeline files.
- API routes export uppercase `GET` and `POST` and set `export const prerender = false`.
- Work on a branch. Do not commit on `main`.
- The worker never passes a bot check by deception. It sends its own user agent `RubberDuckBot`, respects `robots.txt`, and stops on 401, 403 or 429. No browser-like headers, no headless browser, no stealth plugin. A blocked site goes through the browser extension.
- Never commit `.playwright-mcp/`. It holds the screenshots and snapshots of a browser session, and `.gitignore` lists it.

## Build, test, and development commands

- `npm start`: the full local run via `scripts/local.mjs`. It checks Docker, starts local Supabase, applies pending migrations, writes `.env` and `.dev.vars` only when missing, then runs `astro dev`. `--setup-only` stops before `astro dev`. It skips Docker and Supabase when an env file has a cloud `SUPABASE_URL`. Ctrl+C stops only `astro dev`. `npx supabase stop` stops Supabase.
- In an agent session, Astro starts `astro dev` in the background and `npm start` exits 0. The port can differ from 4321. Stop the server with `npx astro dev stop`.
- `npm run dev`: dev server on the Cloudflare workerd runtime. `npm run build`: production SSR build.
- `npm run worker`: `scripts/worker.mjs` starts the background worker on port 8788 with the local Supabase values. It reads the service key into memory only and never prints it. Ctrl+C releases the current job and stops the worker. The check page needs `ENABLE_JOB_CHECK=true`, and the wake request needs `WORKER_WAKE_URL` and `WORKER_WAKE_SECRET`, in `.dev.vars`, as in @.env.example.
- `npm run engine`: `scripts/engine.mjs` starts the topic engine of `engine/` on `127.0.0.1:8790` with the secret `local-engine-secret`. It needs uv. The model source: with no key, the Claude Code bridge on `127.0.0.1:8791`. With `ANTHROPIC_API_KEY` in the env of the command, the Anthropic API. With `--fake`, the fake model of `scripts/fake-model.mjs` on 8791, with no key and no network. `ENGINE_PORT` and `MODEL_PORT` change the ports. `npm run worker` sends its topic jobs to `127.0.0.1:8790` unless `TOPIC_ENGINE_URL` and `TOPIC_ENGINE_SECRET` are set.
- `npm run test:engine`: the engine tests, `pytest` in `engine/` through uv. No server and no model. CI runs them in the `smoke` job.
- `npm run check:engine`: starts the engine with the fake model on free ports, sends the fixture lesson `engine/tests/fixtures/lesson.md`, checks the answer, and stops both.
- `npm run topics:try -- <file.md>`, or `npm run topics:try -- --course <id> --lesson <position>`: sends one lesson to a running engine and prints the topics, the quotes and the relations. It writes nothing to the database.
- `npm run lint`, `npm run lint:fix`, `npm run format`: ESLint with type-checked rules, then Prettier. `npx astro check`: types. CI runs both.
- `npm run test:unit`: the unit tests `worker/**/*.test.ts`, `extension/**/*.test.ts`, `src/**/*.test.ts` and `scripts/**/*.test.mjs`, with `node --test`. No server and no database. CI runs them in the `smoke` job.
- `npm run build:extension`: `extension/build.mjs` bundles the browser extension with esbuild into `extension/dist`, which is gitignored. CI runs it in the `smoke` job.
- `node scripts/fixture-server.mjs`: serves the fixture course site of `scripts/fixtures/course/` on port 8799, with zero dependencies. The start page is `http://localhost:8799/duck-basics`. CI starts it before the worker.
- `npm run smoke`: auth-flow smoke test against a running server, `BASE_URL` default `http://localhost:4321`.
- `npm run phone-check`: `scripts/phone-check.mjs` opens every page at 375px and 320px in headless Chromium and checks the phone rules. Same `BASE_URL` default. One-time setup: `npx playwright install chromium`. CI runs it in the `smoke` job, before the smoke test.
- `npx supabase start`: local Supabase, needs Docker. Node version: @.nvmrc.
- `npx supabase test db`: pgTAP policy tests in `supabase/tests/`. CI runs them in the `smoke` job.
- `npm run db:types`: writes `src/db/database.types.ts` from the local schema. Run it after each schema change.
- `npm run setup:prod`: `scripts/setup-prod.mjs`, the production setup. It creates or reuses the Supabase project, sets up the background worker in Google Cloud (`scripts/setup-google.mjs`, with unit tests), sets the `production` environment secrets and variables in GitHub, and applies the Supabase auth settings and the Send Email Hook. It asks before it replaces a value. A human runs it. The README "Deployment > One-time setup" section has the manual steps.

## Project structure

- `src/pages/`: Astro pages. `src/pages/api/auth/`: sign-in, sign-up, sign-out, reset, new-password, and change-password endpoints. `src/pages/dashboard.astro`: the protected page.
- Password reset: `src/pages/auth/reset.astro`, `src/pages/auth/confirm.ts`, `src/pages/auth/new-password.astro`. `src/lib/recovery.ts`: the guard that accepts only a session from a recent email link. The reset link and the sign-up link both count, because both prove control of the inbox.
- Password change: `src/pages/dashboard/settings.astro`: the settings page with the change form. `src/pages/api/auth/change-password.ts`: the route checks the current password before it saves the new one. Then it signs out all other sessions of the user. Two Supabase settings break it: `secure_password_change = true` makes each change fail, and the `password_changed` notification needs its type in `buildEmail`.
- OAuth login: `src/pages/api/auth/oauth.ts`: the route that starts the GitHub or Google sign-in. `src/pages/auth/callback.ts`: the route that ends it. `src/lib/oauth.ts`: the active provider list from `OAUTH_PROVIDERS`. `OAUTH_PROVIDERS` is a public build-time setting, for example `github,google`. Without it, the pages show no OAuth button. A human registers the OAuth apps and enters the client secrets in `npm run setup:prod`. An agent does not do these steps. The README section "OAuth login" has the steps.
- Auth emails: `src/pages/api/hooks/send-email.ts`: the Supabase Send Email Hook route. It sends the sign-up and reset emails through Resend. `src/lib/email-hook.ts`: the signature check, the email texts, and the quota alert. The hook refuses every other email type with 400, so a new email flow needs its type in `buildEmail`.
- `src/layouts/Layout.astro`: `<head>` and the config banner. `src/layouts/AppLayout.astro`: the shell of the signed-in pages. `src/lib/nav.ts`: the page links and the account links. A new signed-in page imports `AppLayout`, adds one entry to `navLinks`, and adds one `Entry` to the dashboard. An account page, such as Settings, adds one entry to `accountLinks` and gets no dashboard entry. The account links show right before Sign out.
- Looks: `theme` in `src/lib/site.ts` names the active look: `warm`, `editorial`, `calm`, `swiss` or `dock`. `src/lib/looks.ts`: `LOOKS` and `activeLook()`. `src/styles/themes.css`: one token block for each look. `src/themes/<look>/Shell.astro`: the shell of each look. `AppLayout.astro` picks it. `src/components/Entry.astro` and `src/components/EntryList.astro`: a dashboard entry and its container, in the form of the active look. The cookie `look` overrides the look only when `ALLOW_LOOK_OVERRIDE` is true. Production does not set it. `LOOKS=all npm run phone-check` checks all five looks.
- `src/components/`: Astro for static content, React only for interactivity. `src/components/ui/`: shadcn components.
- `src/lib/`: Supabase client, `cn()` helper, services. `src/middleware.ts`: session lookup and `PROTECTED_ROUTES`.
- `supabase/`: local config and migrations. `supabase/tests/`: pgTAP policy tests. `src/db/`: generated database types. `scripts/smoke.mjs`: the smoke test. `context/`: foundation docs and change logs.
- `worker/`: the background worker, plain Node TypeScript. Its dependencies are in `worker/package.json`: `@crawlee/http`, `@crawlee/utils`, `jsdom`, `@mozilla/readability`, `turndown`, and `@anthropic-ai/sdk`, at pinned versions. The root `postinstall` installs them, and the Docker image runs `npm ci --omit=dev`. `main.ts`: the HTTP server with `POST /wake` and `GET /health`. `queue.ts`: the only module that calls the job functions of the database, through the Supabase REST API with the service key. `run.ts`: the job loop. `rules.ts`: the pure rules. `handlers/`: one handler for each job type. A new job type adds one entry to `handlers/index.ts` and its name to the type check of the `jobs` table. The web app must not import from `worker/`, because the worker uses Node APIs and the web app runs on workerd.
- Jobs in the web app: `src/lib/jobs.ts`: the job view, the demo limits, the error texts and `wakeWorker()`. `src/pages/api/jobs/`: start, read and retry a job. `src/components/jobs/JobStatus.tsx` and `src/components/hooks/useJobStatus.ts`: the status, which refreshes every 3 seconds. `src/pages/dashboard/job-check.astro`: the check page. It answers 404 unless `ENABLE_JOB_CHECK` is true, and it has no nav entry. A learner can start and read only their own jobs, and can retry a failed job through `retry_job`. Every other change to a job goes through the worker functions of the database.
- Courses: `worker/courses/` crawls an open course site in the `load_course` job, and `worker/llm.ts` picks the lessons with one model call. Without `ANTHROPIC_API_KEY`, the lesson finder uses its rule: the links under the path of the start page. `src/lib/courses.ts`, `src/pages/api/courses/` and `src/pages/dashboard/courses/`: the load, the reload and the lesson list.
- Topic map: `engine/`: the topic engine, a Python HTTP service with `GET /health` and `POST /extract`. It asks a model for the topics of one lesson through Cognee. uv manages it with `engine/pyproject.toml` and `engine/uv.lock`, and `engine/Dockerfile` builds its image. `worker/handlers/build-topic-map.ts`: the handler of the `build_topic_map` job. `worker/topics/`: its modules: the passage splitter, the engine client, the quote check, the schema check, the topic identity, and the map build. `src/components/topics/`: the map island (React Flow), the panel, the controls, and the outline that the server renders. `src/lib/topics.ts`, `src/pages/api/courses/[id]/topics.ts` and `src/pages/dashboard/courses/[id]/map.astro`: the map state, the start route and the map page.
- Cognee in the engine: `prepare_cognee()` in `engine/rubber_duck_engine/extract.py` sets the retry of the Cognee model call to 1 attempt and wraps `litellm.acompletion`, so the engine reads each stop reason. These reach into Cognee and LiteLLM internals. Before an upgrade of either package, check this function and run `npm run test:engine` and `npm run check:engine`. The engine refuses to start when the Cognee retry is not where the function expects it.
- Marks: a learner marks the topics of a course that they know. `supabase/migrations/20261127230000_create_learner_events.sql`: the append-only table `learner_events`, with one row for each mark or unmark. A learner inserts and reads only their own rows, and nobody changes or deletes a row. `course_topic_list` gives the live topics of a course, and `learner_course_events` gives the events of the learner for a course. No function joins the map with the events. `src/lib/learner-state.ts`: the pure function that gives the state of each topic from the events. `src/lib/marks.ts`: the form rules, the texts, `saveMarks` for the islands, and `readTopicMarks` for the pages. `src/pages/api/courses/[id]/marks.ts`: the marks route. `src/pages/dashboard/courses/[id]/known.astro`: the checklist page. `src/components/topics/KnownTopicList.tsx`: its island. `src/components/hooks/useTopicMarks.ts`: the hook of the checklist and of the "Known" control in the topic panel.
- `extension/`: the browser extension for a site that blocks automated reads. It has its own `package.json`, which the root `postinstall` installs. `extension/src/`: the popup, the background script, the page conversion (Readability, then Turndown), and its unit tests. It saves only the pages that the learner opens, and it sends them with a personal access token to `src/pages/api/extension/`. `src/pages/api/tokens/` and the Settings page create and revoke the tokens.

## Coding style and naming

- Prettier per @.prettierrc.json: 120 columns, double quotes, semicolons. ESLint strict type-checked. Unused variables start with `_`. A `console` call is a warning.
- Import with the `@/*` alias. Merge Tailwind classes with `cn()` from `@/lib/utils`, never by string concatenation.
- Use token classes, never a color name class. For example, use `bg-card`, `text-muted-foreground`, `bg-primary text-primary-foreground` and `border-border`, not `bg-white` or `text-purple-500`. A look changes the app only through the tokens in `src/styles/themes.css`.
- React components: PascalCase `.tsx`, no Next.js directives. Hooks in `src/components/hooks/`. Shared types in `src/types.ts`.
- Migrations: `YYYYMMDDHHmmss_short_description.sql`. Pre-commit: husky runs lint-staged (`eslint --fix`, `prettier --write`).

## Testing

- The unit test runner is `node --test`, for the worker, the extension, the pure modules of the web app in `src/lib/`, and the setup scripts: `npm run test:unit`. The tests use `node:test` and `node:assert`, and sit next to their module as `*.test.ts`, or `*.test.mjs` in `scripts/`. A unit test of the web app covers only a module with no Astro and no browser API, for example `src/lib/topic-map-layout.test.ts`. The smoke script and the phone check test the pages. CI runs the unit tests and the engine tests, then both scripts against the production preview with a local Supabase, a running worker, and the engine with the fake model.
- `SMOKE_JOB_CHECK=1 npm run smoke` adds the job steps: demo jobs to `done` and to `failed`, a retry, and the access checks. They need `ENABLE_JOB_CHECK=true` on the server and `npm run worker`. Without the variable, the smoke test skips them.
- `SMOKE_COURSES=1 npm run smoke` adds the course steps: a load of the fixture course, a second load of the same URL, the access check, and the extension routes with a token and a revoked token. They need `ALLOW_PRIVATE_COURSE_URLS=true` on the server, `node scripts/fixture-server.mjs`, and `ALLOW_PRIVATE_COURSE_URLS=true npm run worker` without `ANTHROPIC_API_KEY`. The extension routes allow 10 calls per minute, so the smoke test sends only 3.
- `SMOKE_COURSES=1 SMOKE_TOPICS=1 npm run smoke` adds the topic steps: the topic job after the load ends with a current map, the map page lists each loaded lesson, an open lesson shows a topic with a quote, the learner marks that topic with a form post and removes the mark with a script request, the marks route refuses a JSON body and a bad topic id, the checklist page lists the topics and shows a new mark, the second learner cannot mark a topic, gets 404 for the checklist and for the map, and cannot insert a topic job, and the start route for an extension course starts a job that ends `done`. They need `npm run engine -- --fake` and a worker that sends its topic jobs to that engine. A learner can start 5 topic jobs in one hour, and the steps start 3 for one learner.
- `npm run phone-check` also loads one course and checks `/dashboard/courses`, the course page, and the checklist page of the course (`<course page>/known`). The load needs `ALLOW_PRIVATE_COURSE_URLS=true` on the server and on the worker. Without it, the check skips the course page. Then it checks the map page and one lesson page of the map. It waits for `data-ready="true"` on the map canvas before it measures. Without a running engine, the course has no map and the check skips the lesson page.
- `npm run phone-check` checks the phone rules on every page. No sideways scroll at 320px, and no element reaches past the right edge. The bar (`data-testid="shell-nav"`) is at most 64px high. Every link and button is at least 44px high and wide. Every input has a font size of at least 16px. A new link or button uses `min-h-11 min-w-11`.
- The phone check has one named exception: the map canvas (`data-testid="topic-map-canvas"`) pans, so the right edge rule skips each element inside it. The canvas itself stays under the rule. The tap size rule stays for each element inside the canvas, except an element that the canvas clips fully. Do not add another exception.

## Commit and pull request guidelines

- Subject: imperative, sentence case, no type prefix, as in `git log`. Body: name the tool that generated the files. Agent commits end with a `Co-Authored-By:` trailer.
- CI gate (@.github/workflows/ci.yml): the `ci` job (lint, `astro check`, build) and the `smoke` job run in parallel. The build needs the `SUPABASE_URL` and `SUPABASE_KEY` repository secrets.

## Security and configuration

- Secrets are server-only via the `astro:env` schema in @astro.config.mjs. Never read them in client code.
- CI deploys `main` to production in the `deploy` job of @.github/workflows/ci.yml. An agent does not run `npx wrangler deploy` by hand.
- `/healthcheck` shows the live version as the commit SHA.
- Human actions only: `npx wrangler rollback`, the Cloudflare API token, and the production secrets. The README "Deployment" section has the steps.
- A human registers the GitHub and Google OAuth apps and enters their client secrets in `npm run setup:prod`.
- The human runs `npm run setup:prod`. An agent does not run it. `SUPABASE_ACCESS_TOKEN` goes only in the env of that one command. It never goes to CI, to a GitHub secret, or to a file.
- `SUPABASE_SERVICE_KEY` passes all access rules. It lives only in Google Secret Manager (`worker-supabase-service-key`), which Cloud Run reads, and in the memory of `npm run worker`. It never goes to the web app, to `.env`, to `.dev.vars`, or to a file.
- `ALLOW_PRIVATE_COURSE_URLS` is for a local run and CI only. Production never sets it, on the web app or on the worker. On the worker it turns off the address check of the crawl, so the worker can read a private address. The `deploy-worker` job does not set it.
- The model key `ANTHROPIC_API_KEY` goes only to the worker and to the engine. In production the worker reads it from Google Secret Manager (`worker-anthropic-api-key`). Locally it goes only in the env of `npm run worker` or `npm run engine`. It never goes to the web app, to `.env`, to `.dev.vars`, to CI, or to a file. CI uses the fake model. The human sets the spend limit in the Anthropic Console.
- The Claude Code bridge (`scripts/model-bridge.mjs`) uses the Claude Code login of the developer. It removes `ANTHROPIC_API_KEY` from each `claude` process. `npm run engine` gives the bridge and the fake model a new key for each start (`MODEL_KEY`). They refuse a request with another key or with an `Origin` header, so a web page in the browser cannot use the login. Start the bridge only through `npm run engine`. It is a local tool for one developer, and it never runs in CI or in production, because the Claude Code terms do not let a product send the requests of its users through a subscription login.
- The human does the Google setup and sets the Google settings in GitHub: `GCP_WORKLOAD_IDENTITY_PROVIDER`, `GCP_SERVICE_ACCOUNT`, `GCP_PROJECT_ID`, `GCP_REGION`, `WORKER_WAKE_SECRET`, `WORKER_WAKE_URL`, `TOPIC_ENGINE_URL` and `TOPIC_MODEL`, and the four Secret Manager secrets. The `deploy-worker` job deploys the worker. The `deploy-engine` job deploys the topic engine with the Anthropic key and `engine-secret` from Secret Manager. An agent does not run `gcloud run deploy`. The README sections "Deployment > Background worker" and "Deployment > Topic engine" have the steps.
